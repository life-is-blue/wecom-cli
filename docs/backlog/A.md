# Backlog A (core correctness gaps noticed, not built)

Conflicts between sources are listed first (decision taken, so the code and `docs/invariants.md` follow it).

| ID | Title | Evidence | Fix | Effort |
| --- | --- | --- | --- | --- |
| A-1 | Source conflict: "PASSED is immutable except through a reject reason" vs the rule table | `m0-naming-spec.md` / the stage rules say a PASSED stage reopens only with a reject reason. `core.builtin` let `pass -> na` through with a `not_applicable` reason (found by the differential test, seed 2, `setstages` on a passed stage). | Fixed in this run (`validate.go`): `pass -> na` is refused; regress first, then mark N/A. Recorded here because the spec never states the N/A case. | done |
| A-2 | `setScope OUT_OF_SCOPE` requires a discard reason only when the scope key changes | `m0-naming-spec.md`: "reason (required when OUT_OF_SCOPE)". `Validate` sees changes only; on an already-out workflow the call changes just `into` (or nothing), so any reason or none is accepted, and a merge can be silently turned into a plain discard. | In `setScope`, load the reason config and require a `discard` reason for every OUT_OF_SCOPE call before no-op elimination. | S |
| A-3 | Events are written for semantic no-ops on never-set keys | `scope=in` on a workflow that never had a `scope` key, `deleted=false` (undelete of a live workflow) or `stage.x=open` on a fresh stage store `absent -> value` and bump the etag although nothing observable changed. Documented as INV-11; the reference model encodes it. | Normalise defaults (absent == `in`/`false`/`open`) in the plan functions, or treat default-valued writes on absent keys as no-ops. | S |
| A-4 | Writes to a soft-deleted workflow are accepted | `advanceStage`, `setScope`, label edits, comment resolve all succeed on a deleted workflow (only comment *creation* checks `WorkflowExists`). The spec is silent; AIP-135 style APIs usually answer FAILED_PRECONDITION/NOT_FOUND. | Decide, then reject writes other than `:undelete` on deleted entities in `Apply`. | S |
| A-5 | `regress` does not cascade | Reopening `verify` leaves a later `accept=PASSED` in place: the stored state has `accept` passed while `verify` is open (current_stage = verify). INV-02 only constrains the moment of a pass. | Decide the product rule (cascade-reopen later stages, or refuse regress while later stages are PASSED). | M |
| A-6 | Filter grammar: implicit AND before a parenthesis is a syntax error | `a=1 (b=2 OR c=3)` fails with INVALID_FILTER; the parser's `peekWord` stops at `(`. Pre-existing. | Treat `(` as the start of the next implicit-AND operand. | S |
| A-7 | `X-Openetl-Channel: cli` is client-asserted and `legacy`/`import` bypass validation | Channel comes from a header for the CLI/API distinction only; `import` and `legacy` are server-set. Not exploitable today, but the bypass list is a single `if` in `Validate`. | Make the channel a server-side property of the entry point (types, not strings). | S |
| A-8 | Admin-role bypass of side rules is unbounded | `Role == admin` satisfies every side rule (also `accept` for a delivery admin). Matches the code and the tests, but the spec only says "admin". | Product decision; if unwanted, restrict to an explicit override reason kind. | S |
| A-9 | Admin lists (members, tokens) still use unsigned offset tokens | Page tokens of lists built with `encodeTok` in `admin.go` are not bound to a query (workflow, task, comment, event and `query` lists are, INV-24). | Reuse `sealPageToken` there. | S |
| A-10 | Merge validation can fail with a deadlock under contention | Two merges that lock each other's chains deadlock; one is retried transparently (up to 4 attempts) but a long chain under heavy contention could exhaust them and surface INTERNAL. | Take one advisory lock per project for merge edges once the app user may use `GET_LOCK` on a dedicated connection (see B-3). | M |
| A-11 | Ack-before-durable depends on MySQL settings | The chaos test (SIGKILL of the server) cannot test power loss; `innodb_flush_log_at_trx_commit` / `sync_binlog` are not asserted by the server at startup. | Startup check that logs a warning when durability settings are weaker than 1/1. | S |
